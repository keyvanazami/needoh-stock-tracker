# Phase 1 — teacher copy

Everything for the first phase. Students get three files; this bundle is the
rest of it.

## Hand out

`student-kit.zip` is ready to distribute as-is — jar, spec, handout, nothing
else. No client code exists anywhere in it, which is the point: students
implement XCHG/1 from the spec in whatever language they like.

| they get | they do not get |
|---|---|
| `xchg-server.jar` | the server source |
| `PROTOCOL.md` — the wire spec | any client, in any language |
| `README.md` — the handout | `TEACHER.md`, `server/` |

Students need a JRE 17+ and nothing else.

## Run it yourself first

```bash
java -jar server/dist/xchg-server.jar
```

UDP on 9001, UI on <http://localhost:9000/>. A built-in market maker is already
quoting, so the book is live with nobody connected.

Worth two minutes before the lab:

```bash
java -jar server/dist/xchg-server.jar --vectors      # what students must reproduce
java -jar server/dist/xchg-server.jar --decode "58 43 01 40 00 00 00 01 00 04 03 61 64 61 C0 15"
java -jar server/dist/xchg-server.jar --link list    # the network conditions
```

## Rebuild

```bash
cd server && ./build.sh      # -> dist/xchg-server.jar, then self-tests the CRC
```

JDK 17+ and nothing else — no Maven, no Gradle, no network, no third-party jars.
The UI page is copied into the jar, so the binary is self-contained. The server
refuses to start if its CRC self-test fails.

Re-zip the student bundle after a rebuild:

```bash
rm -rf out && mkdir -p out/phase1-student-kit
cp PROTOCOL.md README.md server/dist/xchg-server.jar out/phase1-student-kit/
cd out && zip -r ../student-kit.zip phase1-student-kit
```

## Running it for a class

One instance serves everyone. Sessions are keyed by source address and port, so
students trade against each other and the UI attributes every trade to a team.
Rate limiting (200 pkt/s/session) and a 64-order resting cap stop one runaway
loop spoiling it.

```bash
java -jar server/dist/xchg-server.jar --udp-port 9001 --web-port 9000
```

Put the UI on a projector. The packet log answers most questions before they are
asked — it names the reason in words (`ORDER payload is 9 bytes, spec says 11`),
so "it doesn't work" becomes self-service.

Later in the lab, once clients work, turn the network bad:

```bash
java -jar server/dist/xchg-server.jar --link flaky-acks
```

Orders execute but their ACKs mostly do not arrive. Students discover they
cannot tell "my order never arrived" from "the reply was lost", and that
retrying blindly doubles their position. That is the problem Phase 2 exists to
solve, and it is better met as an experience than as a lecture slide.

`--link list` has the rest: `slow`, `busy`, `congested`, `lossy`, `corrupt`,
`quiet-book`, `satellite`, `mobile`. Everything is seeded, so `--seed 7` twice
gives the same run twice — useful when you want every bench hitting the same
conditions.

| path | what it is |
|---|---|

Read `server/README.md` next — it covers the link emulator and how to add new
network conditions.

## Two things to know before you change anything

**The acceptance vectors are generated by the server's own encoder.** `--vectors`
runs the same code path the server uses, so the published spec cannot drift from
the implementation. If you change the wire format, the vectors change with it —
regenerate the worked example in `PROTOCOL.md` from the new output.

**`Link.java` is the only thing that decides a datagram's fate.** It sits between
the socket and the order book, so everything below it is written as if the
network were perfect. A new named condition is one `case` in `Link.applyPreset`
plus a row in `Link.presetHelp()`; nothing else changes.
